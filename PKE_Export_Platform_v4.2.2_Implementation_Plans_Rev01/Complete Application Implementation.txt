# 2. KEPUTUSAN BISNIS YANG TIDAK BOLEH DIUBAH

## 2.1 Cakupan aplikasi

Aplikasi pada tahap awal berfokus sepenuhnya pada ekspor PKE/Palm Kernel Expeller sampai benar-benar matang dan teruji di lapangan.

Arsitektur database dan modul boleh disiapkan agar dapat dikembangkan untuk komoditas lain, tetapi jangan mengimplementasikan komoditas lain sebelum dibutuhkan.

Pengguna aplikasi berasal dari satu perusahaan eksportir, bukan SaaS multi-tenant.

Aplikasi harus mampu menangani sekitar 2–3 proyek aktif secara bersamaan, dengan rancangan yang dapat berkembang ketika volume operasional meningkat.

Negara tujuan awal: China dan Pakistan.

## 2.2 Backend dan storage

Backend utama:
- Neon PostgreSQL.
- Neon paid plan.
- Neon autosuspend/scale-to-zero dinonaktifkan pada production.
- Neon Object Storage / Neon Buckets sebagai storage awal.
- Private bucket untuk dokumen dan bukti operasional.
- Database migrations yang terstruktur.
- Backup serta prosedur restore yang diuji.

Gunakan Storage Adapter agar nantinya penyedia object storage dapat diganti tanpa membangun ulang seluruh modul.

Jangan menggunakan Neon Buckets sebagai pengganti database. Metadata dokumen tetap disimpan di PostgreSQL, sedangkan file disimpan di object storage.

## 2.3 Mata uang

Functional/base currency perusahaan adalah IDR.

Setiap project dapat mempunyai:
- Contract currency.
- Reporting currency.
- Transaction currencies.
- Contract FX baseline.
- Current market/reference rates.
- Actual execution rates.
- FX exposure.
- FX gain/loss.
- FX risk policies.

Kurs awal yang telah disepakati harus disimpan sebagai snapshot dan tidak boleh berubah ketika kurs pasar berubah.

## 2.4 Admin aplikasi

Hanya terdapat satu Admin Application principal.

Admin merupakan satu-satunya pihak yang:
- Membuat dan menyetujui Contract Program.
- Mengaktifkan Contract Program.
- Mengatur recurring cycle.
- Mengatur project configuration.
- Mengaktifkan atau menonaktifkan fitur proyek.
- Menetapkan anggota dan role proyek.
- Mengatur permission dan scope.
- Mengatur buyer/supplier visibility.
- Menyetujui perubahan konfigurasi utama.
- Menetapkan kebijakan sistem.

PM, Finance, dan manager tidak boleh menggantikan otoritas persetujuan Contract Program.

Jika Admin belum menyetujui, Contract Program harus tetap menunggu.

Lindungi akun Admin dengan MFA, session management, audit log, dan pembatasan akses. Jangan membuat akun Admin tambahan secara otomatis.

## 2.5 Contract Program dan recurring project

Pisahkan:
- Buyer Contract.
- Contract Program.
- Recurring Cycle Schedule.
- Project Instance.
- Shipment.
- Vessel Voyage.
- Payment Settlement.

Satu kontrak buyer dapat berlangsung selama beberapa tahun.

Contoh:
- Kontrak 5 tahun.
- Target 10.000 MT per bulan.
- Pembayaran buyer per pemenuhan 10.000 MT.

Setiap periode pemenuhan menjadi Project Instance tersendiri.

Satu Project Instance dapat memiliki beberapa shipment dan voyage.

Project Instance tidak boleh dianggap selesai hanya karena barang sudah dimuat ke kapal. Project baru dinyatakan closed-settled sesuai kebijakan penutupan ketika kewajiban pembayaran buyer dan seluruh persyaratan settlement telah diselesaikan.

Pembayaran parsial tidak menutup project.

Recurring cycle harus diatur oleh Admin sejak awal dan dapat diubah selama project berjalan dengan versioning dan audit trail.

## 2.6 Amendment

Ketika ada perubahan hasil negosiasi buyer dan supplier, aplikasi menyediakan beberapa alternatif penanganan:
- Amendment record.
- Versioned project configuration.
- Project baru.
- Supplemental project.
- Split cycle.
- Merge cycle jika secara komersial dan akuntansi diperbolehkan.
- Pause atau cancellation.

Admin memilih cara pencatatan berdasarkan dokumen dan instruksi komersial yang telah disepakati para pihak.

Jangan menganggap perubahan harga, mata uang, supplier, kuantitas, atau jadwal selalu harus menghasilkan project baru.

Transaksi historis tidak boleh ditimpa atau diubah tanpa audit.

## Definition of Ready for First Real Project

Project ekspor pertama hanya boleh diaktifkan setelah:

1. Seluruh scope P01–P13 yang diwajibkan telah diimplementasikan.
2. Tidak ada defect Critical atau High yang belum diselesaikan.
3. Tidak ada known blocking bug pada acceptance criteria.
4. Seluruh integration dan security tests lulus.
5. Financial reconciliation tests lulus.
6. Semua permission dan RLS tests lulus.
7. Semua API penting mempunyai error handling.
8. Backup dan restore telah diuji.
9. Admin menyetujui konfigurasi produksi.
10. UAT dan pilot preparation telah diselesaikan.

Tidak boleh menjanjikan zero bugs absolut. Setiap temuan baru wajib masuk issue tracking, ditangani berdasarkan severity, dan diuji ulang.

# 10. ATURAN PENTING TENTANG PERUBAHAN DAN OPERASI

Jangan melakukan tindakan destruktif:
- Jangan drop database.
- Jangan menghapus migration lama.
- Jangan menghapus file atau konfigurasi yang sudah ada.
- Jangan mengganti schema production secara langsung.
- Jangan menjalankan command yang menghapus data tanpa backup dan persetujuan eksplisit.
- Jangan mengirim data rahasia ke layanan eksternal tanpa izin dan kebijakan yang sesuai.

Gunakan database terpisah untuk development, staging, dan production.

Jangan menggunakan database production untuk test.

Jangan melakukan deploy production tanpa persetujuan pemilik proyek.

Jangan meminta API key sampai tahap integrasi yang memang memerlukannya.

Saat membutuhkan API key:
- Buat `.env.example`.
- Beritahu nama environment variable.
- Jelaskan layanan yang membutuhkan key.
- Jangan meminta user menempelkan key ke chat atau source code.
- Pastikan `.env` masuk `.gitignore`.
